### 3. **Key Classes & Their Roles**
Let’s examine each class:

#### `EventletAdaptedEvent`
- A thin wrapper over event-like synchronization for Eventlet (green threads).
- Purpose: make native threading-style events work in eventlet's cooperative model.

#### `Drainer`, `greenletDrainer`, `eventletDrainer`, `geventDrainer`
- These are *drainers*: components that drain events from a message channel (e.g., AMQP) until a condition is met (e.g., result received).
- The `register_drainer` decorator marks specific drainers for use (eventlet vs gevent).
- Core pattern: they integrate with async I/O loops (eventlet/gevent) to avoid blocking while waiting for results.
- Used specifically in **async result backends** (e.g., when using Redis or RPC backend with eventlet/gevent pool).

#### `AsyncBackendMixin`
- Mixin adding async-capable methods: `_collect_into`, `iter_native`, `add_pending_result`, `wait_for_pending`, `_wait_for_pending`, etc.
- Clearly designed to be mixed into a *result backend* to support non-blocking waiting for results.
- Methods like `on_result_fulfilled`, `is_async`, `_maybe_resolve_from_buffer` indicate integration with result buffering and resolution logic.

#### `BaseResultConsumer`
- Manages consumption of result messages (e.g., from AMQP for RPC backend).
- Has methods like:
  - `drain_events`, `drain_events_until`
  - `on_state_change`, `on_out_of_band_result`
  - `_get_pending_result`, `cancel_for`, `consume_from`
- This is the core consumer logic for result backends — especially for *asynchronous* backends where results arrive out-of-band.

> Crucially, this class is **not** part of the worker’s main task consumer (which consumes *task* messages), but rather the *result* consumer — i.e., it listens for task *results* (e.g., via AMQP reply-to queues in RPC backend).
