### 2. **What is a Bootstep?**
In Celery, bootsteps are part of the **worker’s internal architecture**, used to extend or modify the worker's behavior during startup, shutdown, or runtime. They are managed by the `celery.worker` module, specifically via `celery.worker.bootsteps` and consumed by the `Consumer` and `Worker`.

The `DelayedDelivery` class:
- Is activated conditionally based on consumer/queue type (`include_if`)
- Runs during worker start (`start`)
- Interacts directly with `Consumer`, `Connection`, and broker-specific Kombu features
- Handles setup of exchanges/queues for *native delayed delivery* — a transport-level feature tied to worker operation

This is not:
- An **app**-level concern (no task registration, config loading, routing logic).
- A **backend** (no result storage or retrieval).
- A **concurrency** pool (not about prefork/thread/eventlet).
- A **contrib** extension (this is core functionality, not an add-on like Django integration).
- An **events** module (no event emission/reception).
- A **fixups** module (no framework-specific startup patching).
- A **loaders** module (no config/task import logic).
- A **security** module (no signing, serialization security).
- A **utils** module (though it uses utilities, the class itself is a structured component, not a utility function).
